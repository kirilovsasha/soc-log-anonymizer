🕵️ Инструмент для SOC-аналитиков: маскирует чувствительные данные в логах
(IP-адреса, логины, email, хэши, SID, GUID, MAC, JWT, секреты и т.д.)
перед их отправкой во внешнюю LLM и позволяет восстановить исходные
значения в полученном ответе.

🐍 **Только стандартная библиотека Python** (`re`, `hashlib`, `hmac`, `json`,
`csv`, `argparse`, `tkinter`, `concurrent.futures`, `difflib`, `webbrowser`,
`threading`, `logging`, `configparser`, `dataclasses`, `functools`, `gc`,
`gzip`, `mmap`, `signal`, `atexit`, `tracemalloc`, `cProfile`) — без
внешних зависимостей и без базы данных.

🖥️ Доступен как GUI (tkinter), ⌨️ CLI (для пайплайнов/автоматизации) и как
🧩 Python-библиотека.

<a id="features"></a>
## Возможности ✨

- 🔍 Регэксп-детекция и консистентная псевдонимизация: IPv4 и **IPv6 (в т.ч.
  сжатая форма `::`, RFC 5952 — самая частая в реальных логах, и запись
  `[адрес]:порт` из RFC 3986)**, CIDR/порты, email, телефоны, FQDN, MAC,
  Windows SID, GUID/UUID, хэши (MD5/SHA1/SHA256/NTLM), JWT, base64-команды
  PowerShell, CEF/syslog key=value пары, Windows-логины `DOMAIN\user`,
  пути к профилям пользователей, секреты (`password=`, `token=`...).
  IP-кандидаты дополнительно проверяются через stdlib `ipaddress` — синтаксически
  похожие, но не являющиеся адресом строки (таймстамп `12:30:45`,
  MAC-подобные последовательности) не маскируются по ошибке.
- 🖧 Из коробки распознаёт форматы **syslog** (auth-конструкции sshd/su:
  `Accepted/Failed password for`, `session opened for user`, `'su root'`
  без key=value), **Cisco ASA/IOS** (`for user "admin"`, `Uname: admin`,
  `by admin on vty0`, `User 'admin' executed...` — аудит CLI-команд,
  вложенные квадратные скобки `[user: admin][ip: ...]`) и **Checkpoint**
  (`Subject: admin`, `suser=`/`duser=` наравне с `user=`) — имена
  пользователей в "естественном языке", без разделителя `=`/`:`, тоже
  маскируются, а не только в key=value парах. Соседние key=value пары
  без пробела между ними (`(src=X)(dst=Y)`, частый Cisco/Checkpoint
  формат) обрабатываются корректно — без потери второго поля. Обычные
  английские фразы вида `Invalid password` (сообщение об ошибке, не
  поле) не путаются с полем `password:`, даже если дальше по строке
  встречается несвязанный разделитель Cisco ASA (`field1 = val1 : field2
  = val2`). Список распознаваемых имён полей настраивается
  (`user_field_names`, `secret_field_names`, `cef_fields`) под
  конкретную инфраструктуру.
- 🧬 "Умная" анонимизация JSON и NDJSON по чувствительным ключам, без
  повреждения структуры документа — включая ВЛОЖЕННЫЕ структуры вида
  `{"subject": {"account": {"name": "..."}}}`, характерные для
  нормализованных событий SIEM (**MaxPatrol 10** и подобные): один и тот
  же список `sensitive_json_keys` работает и для плоских ключей
  (`SubjectAccountName`), и для вложенных путей (`subject.account.name`).
- 🔁 Одно и то же значение везде получает один и тот же псевдоним
  (см. [ниже](#pseudonymization)).
- 🔑 **HMAC-SHA256 с ключом, растянутым через PBKDF2** (см.
  [Security](#security)), защита от коллизий хэша,
  `secrets.compare_digest` при сравнении псевдонимов.
- ⏱️ **Базовая защита от ReDoS**: обработка текстового блока выполняется с
  таймаутом (`config.regex_timeout_seconds`); при превышении — явный
  маркер вместо потенциально частично замаскированного текста.
- 🧹 `SOCLogAnonymizer` — контекстный менеджер, явно очищающий чувствительные
  данные из памяти (`with SOCLogAnonymizer(...) as a: ...`).
- ✅ Gatekeeper-проверка (`verify()`) итогового текста перед отправкой в LLM.
- 🔓 Полная деанонимизация ответа LLM обратно в исходные значения;
  mapping-файлы версионируются (`schema_version`) для совместимости.
- 🗜️ **Прозрачная поддержка gzip-архивов** (`app.log.gz`) на чтение — во
  всех режимах (обычном, `--stream`, `batch`), без ручной распаковки;
  распознаётся по магическим байтам, а не только по расширению `.gz`.
- ⌨️ CLI для встраивания в SOC-пайплайны: одиночные файлы, glob-шаблоны
  нескольких файлов, stdin/stdout, построчный стриминг для больших
  файлов (в т.ч. через `mmap`), параллельная обработка, пакетная
  (`batch`) обработка целых каталогов логов с сохранением
  консистентности псевдонимов между файлами, проверка конфигурации
  (`validate-config`), профилирование (`--profile`/`--profile-memory`),
  корректная обработка SIGINT/SIGTERM, `--version`.
- 📝 **`logging`** с уровнями (`-v`/`-vv`) и файлом журнала (ротация), **коды
  возврата** (0/1/2) для встраивания в CI/пайплайны (`--fail-on-unsafe`),
  предупреждения о больших файлах и небезопасных правах доступа к
  секретным файлам (соль/mapping).
- 🖥️ GUI: подсветка замен по типу данных прямо в паре Input/Output сразу
  после анонимизации (без перехода на другую вкладку), отдельный
  HTML Diff отчёт по кнопке (для отправки/печати), реальный прогресс-бар,
  статистика по сессии, отмена последней операции (undo), автоочистка
  таблицы соответствия по таймауту, горячие клавиши, тёмная тема,
  настраиваемый размер шрифта, экспорт таблицы в CSV/JSON с
  ограниченными правами доступа, placeholder-подсказки, живая проверка
  энтропии соли, автосохранение черновика с восстановлением после сбоя
  (файл черновика — с правами 0600), tooltip с контекстом в таблице
  соответствия, программно сгенерированная иконка окна (без сторонних
  файлов/Pillow).
- 🧾 Опциональный структурированный аудиторский журнал операций
  (JSON Lines, `audit_log_path`) — кто/когда/сколько значений какого
  типа заменил, без единого исходного значения или псевдонима; работает
  одинаково в CLI и GUI.
- ⚙️ Настраиваемая конфигурация (список чувствительных JSON-ключей,
  доменные суффиксы, телефонные префиксы, PBKDF2-итерации, порог
  размера файла и т.д.) через **JSON или INI**-файл, с валидацией
  (`validate()` / `validate-config`).
- 🧪 Юнит-тесты на `unittest` (+ `unittest.mock` для CLI, `doctest` для
  рабочих примеров в docstring'ах, самописный fuzz-тест на `random`,
  и логика GUI вынесена в модуль без зависимости от `tkinter` —
  тестируется в любом окружении).

<a id="installation"></a>
## Установка 📦

Требуется Python 3.8+. Модуль `tkinter` (для GUI) обычно идёт в
комплекте с Python; в некоторых Linux-дистрибутивах нужно доставить
системный пакет отдельно (`sudo apt install python3-tk` /
`sudo dnf install python3-tkinter`). Для CLI и библиотеки `tkinter` не требуется.

### Вариант 1 — запуск без установки 🚀

```bash
git clone https://github.com/<your-org>/soc-log-anonymizer.git
cd soc-log-anonymizer
python3 -m soc_log_anonymizer            # GUI
python3 -m soc_log_anonymizer anonymize -i raw.log --salt-file salt.txt
```

### Вариант 2 — установка через pip (editable, локально из репозитория) 🐍

```bash
pip install -e .
soc-log-anonymizer                        # GUI
soc-log-anonymizer anonymize -i raw.log --salt-file salt.txt
```

### Вариант 3 — единый исполняемый файл (`zipapp`, только stdlib) 🗜️

```bash
python3 -m zipapp soc_log_anonymizer -m "soc_log_anonymizer.__main__:main" \
    -o anonymizer.pyz -p "/usr/bin/env python3"

./anonymizer.pyz                          # GUI
./anonymizer.pyz anonymize -i raw.log --salt-file salt.txt
```

Удобно для распространения внутри команды одним файлом без риска, что
кто-то запустит устаревшую копию модулей по отдельности.

### Вариант 4 — автономный исполняемый файл (PyInstaller, Python не нужен) 💾

В отличие от варианта 3 (`zipapp`, всё ещё требует установленный
Python), PyInstaller собирает полностью автономный бинарник — удобно
раздавать SOC-аналитикам, которым не хочется объяснять, как ставить
Python. Требует PyInstaller (`pip install pyinstaller`) только на
машине, где производится сборка — у получателей файла никаких
зависимостей не требуется.

```bash
pip install pyinstaller
pyinstaller packaging/soc_log_anonymizer_gui.spec
# результат: dist/soc-log-anonymizer-gui(.exe)
```

Спека собирает именно GUI (`--onefile`, без консольного окна на
Windows/macOS). Для CLI используйте варианты 1–3 выше — автономная
сборка CLI не даёт заметных преимуществ перед `zipapp`, так как CLI и
так требует терминала и обычно уже используется там, где Python есть
(CI/pipeline, сервер).

Собранный бинарник крупнее (~30–60 МБ, весь интерпретатор Python
упакован внутрь) и должен собираться отдельно под каждую целевую ОС
(PyInstaller не кросс-компилирует) — если нужны сборки под Windows,
macOS и Linux, собирайте на соответствующей ОС или в CI-матрице.

### Windows 🪟

Требуется установленный [Python 3.8+](https://www.python.org/downloads/)
(при установке отметьте галочку **"Add python.exe to PATH"**). После
этого никакой дополнительной установки не нужно — в репозитории есть
готовые `.bat`-файлы:

| Файл | Назначение |
|---|---|
| `run_gui.bat` | Двойной клик — запускает GUI **с видимой консолью диагностики** (показывает найденный Python, проверяет `tkinter`, выводит полный traceback при ошибке) |
| `run_gui_silent.bat` | То же самое, но без окна консоли — используйте только после того, как `run_gui.bat` подтверждённо работает. При ошибке пишет её в `gui_error.log` рядом с файлом и открывает его в «Блокноте» |
| `soc-log-anonymizer.bat` | CLI-обёртка: `soc-log-anonymizer.bat anonymize -i raw.log -o clean.log --salt-file salt.txt`. Без аргументов запускает GUI |
| `setup_venv.bat` | Опционально: создаёт изолированное окружение `.venv` и ставит пакет через `pip install -e .` |

```bat
:: PowerShell / cmd.exe, из каталога проекта
soc-log-anonymizer.bat anonymize -i raw.log -o clean.log --salt-file salt.txt --stats
soc-log-anonymizer.bat batch --input-dir logs --output-dir clean_logs --salt-file salt.txt
```

Совет: добавьте каталог проекта в переменную `PATH` (или создайте ярлык
на `run_gui.bat` на рабочем столе), чтобы запускать инструмент из
любого места одной командой/двойным кликом.

#### Если `run_gui.bat` не запускается

`run_gui.bat` всегда держит консоль открытой и печатает диагностику —
не закрывайте окно сразу, прочитайте, на каком шаге возникла ошибка:

1. **«Python не найден в PATH»** — на новых установках Windows команда
   `python` может открывать Microsoft Store вместо реального
   интерпретатора (это заглушка/alias, а не ошибка скрипта).
   Отключите её: **Параметры → Приложения → Дополнительные параметры
   приложений → Псевдонимы выполнения приложений** → выключите
   `python.exe`/`python3.exe` — затем поставьте настоящий Python с
   [python.org](https://www.python.org/downloads/), отметив **"Add
   python.exe to PATH"**.
2. **«Отсутствует модуль tkinter»** — переустановите Python обычным
   установщиком с python.org, не снимая ничего в списке компонентов
   (стандартный установщик ставит `tkinter` по умолчанию; версии из
   Microsoft Store иногда его не включают).
3. **Traceback после «--- Запуск GUI ---»** — это реальная ошибка
   Python внутри приложения; текст ошибки под заголовком и есть причина.
4. Если после этого хотите запускать без окна консоли — используйте
   `run_gui_silent.bat` (ошибки при этом попадут в `gui_error.log`).

<a id="quick-start"></a>
## Быстрый старт ⚡

```bash
# 1. Сгенерировать и сохранить соль (один раз на инцидент/команду)
python3 -c "import secrets; print(secrets.token_hex(16))" > salt.txt

# 2. (опционально) Проверить конфигурацию перед использованием
python3 -m soc_log_anonymizer validate-config examples/sample_config.json

# 3. Анонимизировать лог
python3 -m soc_log_anonymizer anonymize \
    -i examples/sample.log -o clean.log \
    --org bank --salt-file salt.txt \
    --save-mapping mapping.json --stats -v

# 4. Отправить clean.log в LLM, получить ответ в response.txt

# 5. Восстановить исходные значения в ответе
python3 -m soc_log_anonymizer deanonymize \
    -i response.txt -o restored.txt --mapping mapping.json
```

```bash
python3 -m soc_log_anonymizer gui
```

| Шрифт | Размер шрифта в текстовых полях (8–18 пт) |
| Таблица соответствия | Наведение курсора на строку показывает всплывающую подсказку с контекстом — где именно в исходном логе встретилось это значение |
| Вкладка «Таблица соответствия» | Полный список замен, поиск, экспорт в CSV/JSON |
| Вкладка «⚙ Конфигурация» | Редактирование и сохранение конфигурации прямо в GUI, включая открытие произвольного существующего файла (см. [Редактирование конфигурации в GUI](#config-gui)) |

Длинные строки в Input/Output переносятся по словам на ширину окна
(`wrap=tk.WORD`) — горизонтальной прокрутки нет, длинную строку лога не
нужно листать вбок.

Если после анонимизации отредактировать (напечатать, вставить, удалить
текст) содержимое **Input**, поле **Output** автоматически очищается —
чтобы не отправить/скопировать результат, относящийся к уже изменившемуся
исходному тексту. Программные операции (переключение placeholder-подсказки,
undo) на это не влияют.

**Подсветка различий прямо в Input/Output.** Сразу после «Анонимизировать»
(без отдельного клика или перехода на другую вкладку) в **левом** окне
подсвечиваются исходные значения, которые были заменены — тем же цветом
по ТИПУ данных (IP/EMAIL/SECRET/...), что и их псевдонимы в правом окне.
Так сразу видно, ЧТО именно поменялось, глядя на пару Input/Output.
Наведение курсора на подсвеченное значение в Input показывает tooltip с
конкретным псевдонимом («→ заменено на `[IP_ab12cd34ef56]`») — не нужно
идти в отдельную таблицу соответствия за этой информацией. Для логов с
большим числом уникальных значений подсветка обрабатывается пакетами
(через событийный цикл Tk), чтобы не подвешивать интерфейс.

Отдельный **HTML Diff отчёт** (кнопка «🔀 HTML Diff отчёт», открывается в
браузере) построчно показывает исходный ("-") и анонимизированный ("+")
текст с контекстными строками вокруг изменений; цветным фоном выделены
именно заменённые значения (не поиск похожести строк как
последовательностей символов, а прямой поиск по фактической таблице
соответствия) — исходное значение и его псевдоним подсвечены одним и тем
же цветом, чтобы было видно, что во что превратилось. Внизу отчёта —
подробная легенда: что означает каждый цвет/тип и в каком формате такие
значения обычно встречаются в логе.

**Синхронный скролл.** Чекбокс «Синхронный скролл» синхронизирует
прокрутку левого и правого окна, когда они видны одновременно —
работает при скролле колесом мыши, стрелками и `PageUp`/`PageDown`, а не
только при перетаскивании самого скроллбара.

Таблица соответствия автоматически очищается из памяти после периода
бездействия (по умолчанию 20 минут, настраивается через
`session_timeout_minutes` в конфиге) — экспортируйте её заранее, если
понадобится деанонимизация позже. При закрытии окна и при «Очистить
всё» чувствительные данные также явно очищаются (`clear_sensitive_data()`).

**Автосохранение и восстановление черновика.** Содержимое левого поля
ввода автоматически сохраняется во временный файл каждые 30 секунд. При
следующем запуске, если найден черновик от предыдущей (аварийно
завершённой) сессии, GUI предложит его восстановить. При штатном
закрытии окна файл черновика удаляется.

## CLI ⌨️

```
soc_log_anonymizer --version
soc_log_anonymizer anonymize   [файлы...] [-i IN] [-o OUT] [опции]
soc_log_anonymizer scan        [файлы...] [-i IN] [опции]
```

`--version` — работает и без указания подкоманды, полезно для проверки,
какая версия инструмента установлена/распакована в `zipapp`.

Общие для всех подкоманд флаги: `-v`/`-vv` (детализация лога),
`--log-file PATH` (журнал работы инструмента с ротацией; в него пишутся
только метаданные операций — какой файл, сколько замен, — НЕ содержимое
логов). CLI перехватывает SIGINT/SIGTERM для корректного завершения
(вместо мгновенного обрыва, не дающего отработать очистку памяти) и
регистрирует `atexit`-очистку чувствительных данных как страховку.

`validate-config` дополнительно проверяет типы полей и конфликты
нормализованных JSON-ключей.

### Изменения (2.1.x)

- GUI поддерживает импорт нескольких файлов и папки, разделяет содержимое
  визуальным разделителем, сообщает о частично повреждённых/недоступных
  файлах и позволяет отменить загрузку или обработку.
- Конфигурации получили `config_version`; mapping сохраняет метаданные
  алгоритма при полной обратной совместимости старых файлов.

**Gzip-архивы** (`app.log.gz`) принимаются как входной файл (`-i`) во
всех подкомандах и режимах (обычном, `--stream`, `batch`, multi-file) без
какой-либо специальной настройки — распознаются по магическим байтам
заголовка, поэтому расширение файла может быть каким угодно. В `--mmap`
для `.gz`-файлов автоматически используется gzip-поток вместо mmap (на
диске лежат сжатые байты, не текст). При записи результата суффикс
`.gz` из имени выходного файла убирается (`batch`/multi-file) — сам
результат анонимизации всегда обычный текст, инструмент не архивирует
вывод.

### `anonymize` 🔒

```bash
python3 -m soc_log_anonymizer anonymize \
    -i raw.log -o clean.log \
    --org bank \
    --salt-file salt.txt \
    --config myconfig.json \
    --save-mapping mapping.json \
    --stats --diff --fail-on-unsafe -v
```

- `files...` (позиционные аргументы) — один или несколько файлов/glob-
  шаблонов вместо `-i`, например `anonymize logs/*.log --output-dir clean/`.
  При нескольких файлах обязателен `--output-dir`.
- `--stream` — построчная обработка с постоянным потреблением памяти,
  для очень больших файлов (не разбирает JSON, растянутый на много строк —
  см. [ограничения](#limitations)). Без `--workers`/`--mmap`
  читает файл лениво построчно (не грузит его в память целиком).
- `--mmap` — вместе с `--stream` (однопоточный режим) читает файл через
  `mmap` вместо обычного `open()` — эффективнее на очень больших файлах
  (десятки ГБ) на быстрых дисках. Кодировка определяется по первому
  64КБ-сэмплу файла (без поддержки UTF-16 без BOM — см. ограничения).
- `--workers N` — параллельная обработка чанков строк через
  `ProcessPoolExecutor` (используется вместе с `--stream`; при этом файл
  всё же читается целиком для деления на чанки — параллелизм и
  потоковая экономия памяти здесь являются альтернативами, а не
  складываются).
- `--profile` — профилирует CPU через `cProfile`, top-20 функций по
  cumulative time выводится в лог на уровне INFO (нужен `-v`).
- `--profile-memory` — отслеживает пиковое потребление памяти через
  `tracemalloc`, результат — в лог на уровне INFO.
- `--fail-on-unsafe` — вернуть код возврата `2`, если gatekeeper
  (`verify()`) нашёл потенциально незамаскированные данные (удобно для
  автоматической блокировки отправки в CI/пайплайне).
- `--salt-file` предпочтительнее `--salt`: соль, переданная аргументом
  командной строки, может попасть в историю shell/список процессов.
  Также можно задать переменной окружения `SOC_ANON_SALT_FILE`. Если
  файл соли на POSIX доступен на чтение другим пользователям —
  выводится предупреждение (не блокирует выполнение).
- `--strict-perms` — превращает предупреждение о world-readable
  `--salt-file` (или `--mapping` в `deanonymize`) в жёсткий отказ
  (код возврата `1`) вместо просто записи в лог. Доступен также для
  `deanonymize` и `batch`.
- `--strict-config` — для `anonymize`, `batch` и `scan` превращает
  предупреждения `validate()` в отказ до обработки входных данных.
- `scan --format jsonl|json|csv` выбирает потоковый JSON Lines (по умолчанию),
  единый JSON-массив или CSV-отчёт с размером файла, количеством замен,
  типами, безопасностью и проблемами.
- `batch --dry-run` анализирует все найденные файлы и печатает отчёт без
  создания результатов. `SOC_ANON_ORG` и `SOC_ANON_REPORT_FORMAT` могут
  задавать организацию и формат отчёта через окружение.
- `batch --progress` печатает в `stderr` человекочитаемый прогресс,
  скорость (файлов/сек) и ETA. `batch --progress-events` вместо этого
  выдаёт JSON Lines-события с полями `completed`, `total`, `percent`,
  `rate_files_per_second` и `eta_seconds`; stdout остаётся пригодным для
  отчёта/пайплайна.
- `scan` также сообщает число строк и позиции изменённых фрагментов; для
  больших файлов JSONL остаётся потоковым по одному отчёту на файл.
  Флаг `scan --stream` обрабатывает файл построчно и выдаёт JSONL-события
  по мере чтения.
- `validate-config --fix` сохраняет нормализованную конфигурацию, а
  `diff-config A B` показывает различия.
- `custom_patterns` позволяет явно добавить собственные regex-типы. Поле
  опционально и по умолчанию пусто, поэтому стандартное поведение не меняется.
- XML и YAML-файлы читаются как обычный текст без обязательных зависимостей;
  XML/YAML-структура не изменяется специальным парсером, что обеспечивает
  безопасный graceful fallback в стандартной библиотеке.

### `scan` 🔎

### `verify-result` ✅

Проверяет уже записанные результаты `verify()` и ничего не
анонимизирует/не перезаписывает. Можно передать файлы или каталог:

```bash
python3 -m soc_log_anonymizer verify-result clean/*.log \
    --salt-file salt.txt --fail-on-unsafe --format json
python3 -m soc_log_anonymizer verify-result --input-dir clean \
    --pattern "*.log" --salt-file salt.txt
```

По умолчанию отчёт JSONL печатается в stdout. Доступны `json` и `csv`;
`--fail-on-unsafe` возвращает код `2`, если хотя бы один результат
небезопасен (ошибка чтения возвращает `1`).

`scan` читает входные файлы, выполняет тот же анализ и печатает по одному
JSON-отчёту на файл (`input`, `replacements`, `stats_by_type`), но ничего
не записывает и не сохраняет mapping. Это удобно для предварительной
проверки пайплайна:

```bash
python3 -m soc_log_anonymizer scan logs/*.log --salt-file salt.txt
```

Файловые результаты CLI записываются атомарно через временный файл в том
же каталоге и замену `os.replace`: прерванный запуск не оставляет
частично перезаписанный лог. Таблица соответствия по-прежнему является
секретом и должна храниться с ограниченными правами; шифрование
mapping-файлов намеренно не является частью проекта — используйте
защищённое хранилище/шифрование диска и `--strict-perms`.
- Если входной файл (без `--stream`) превышает `max_input_size_mb` из
  конфига (по умолчанию 500 МБ) — выводится предупреждение с
  рекомендацией использовать `--stream`.
- `-i -` / без `-i` — чтение из stdin; `-o -` / без `-o` — вывод в stdout
  (удобно для конвейеров: `cat raw.log | ... | llm-cli | ... deanonymize`).

### `deanonymize` 🔓

Каждый запуск CLI — новый процесс, поэтому таблица соответствия не
хранится в памяти между вызовами: её нужно было явно сохранить флагом
`--save-mapping` на шаге анонимизации и передать через `--mapping`.

```bash
python3 -m soc_log_anonymizer deanonymize \
    -i llm_response.txt -o restored.txt --mapping mapping.json
```

### `batch` 📁

Обрабатывает каталог логов рекурсивно (`os.walk`), сохраняя
относительную структуру подкаталогов в выходном каталоге. Использует
**одну и ту же соль для всех файлов** — обязательное условие
консистентности псевдонимов между файлами одного инцидента.

```bash
python3 -m soc_log_anonymizer batch \
    --input-dir ./logs --output-dir ./clean_logs \
    --pattern "*.log" \
    --salt-file salt.txt --save-mapping mapping.json \
    --workers 4 --stats --fail-on-unsafe
```

`--workers N` в `batch` распараллеливает обработку **по файлам**
(`ProcessPoolExecutor`), после чего таблицы соответствия всех воркеров
объединяются в главном процессе перед сохранением. `--profile`/
`--profile-memory` работают так же, как в `anonymize`.

### `validate-config` ✅

Проверяет JSON/INI-конфигурацию на очевидные ошибки (пустые списки TLD/
CEF-полей, подозрительно малое число итераций PBKDF2 и т.д.) до того,
как опечатка в конфиге приведёт к «тихой» дыре в маскировании.

```bash
python3 -m soc_log_anonymizer validate-config myconfig.json
```

<a id="library"></a>
## Использование как библиотеки 🧩

```python
from soc_log_anonymizer import SOCLogAnonymizer, AnonymizerConfig

config = AnonymizerConfig.load("myconfig.json")  # .json или .ini, или AnonymizerConfig() для дефолтов
issues = config.validate()
if issues:
    print("Проблемы конфигурации:", issues)

# Контекстный менеджер — гарантирует явную очистку mapping_table/
# reverse_mapping из памяти по выходу из блока.
with SOCLogAnonymizer(salt="случайная-соль", org_name="bank", config=config) as anonymizer:
    clean_text = anonymizer.anonymize(raw_log_text)
    is_safe, issues = anonymizer.verify(clean_text)

    # ... отправка clean_text в LLM ...

    restored = anonymizer.deanonymize(llm_response_text)
    print(anonymizer.get_stats())            # {'IP': 12, 'EMAIL': 3, ...}
    anonymizer.save_mapping("mapping.json")   # права доступа 0600 — сохранить ДО выхода из блока

# После выхода из `with` mapping_table/reverse_mapping уже очищены.

# Восстановление в новом процессе/сессии
anonymizer2 = SOCLogAnonymizer.load_mapping("mapping.json")
restored2 = anonymizer2.deanonymize(llm_response_text)

# Построчный стриминг (низкое потребление памяти)
with open("huge.log", encoding="utf-8") as f, open("clean.log", "w", encoding="utf-8") as out:
    for line in anonymizer2.anonymize_stream(f):
        out.write(line)

# Параллельная обработка списка строк
lines = raw_log_text.splitlines(keepends=True)
clean_lines = anonymizer2.anonymize_parallel_lines(lines, workers=4)
```

<a id="configuration"></a>
## Конфигурация ⚙️

Все настраиваемые параметры вынесены в `AnonymizerConfig`
(`soc_log_anonymizer/config.py`) и могут быть переопределены JSON- или
INI-файлом (формат определяется по расширению `.json` / `.ini`/`.cfg`)
— см. `examples/sample_config.json`:

| Поле | Назначение |
|---|---|
| `org_name` | Название организации, маскируется как `[ORG_...]` |
| `org_aliases` | Альтернативные написания/сокращения названия организации (например, `["Bank of Example", "BoE"]`) — маскируются наравне с `org_name` |
| `org_aliases_share_pseudonym` | По умолчанию `false` — `org_name` и каждый `org_alias` получают РАЗНЫЕ псевдонимы (разные строки => разный хэш), даже если по смыслу это одна организация. При `true` — все буквальные упоминания сходятся к одному псевдониму от `org_name`; **не затрагивает** домены/email, где название организации входит как часть строки (`example.com` продолжает маскироваться самостоятельно как `[FQDN_...]`). Деанонимизация при `true` всегда восстанавливает каноническое `org_name`, а не конкретный алиас, встретившийся в этом месте текста |
| `hash_len` | Длина усечения HMAC-SHA256 в hex-символах (по умолчанию 12) |
| `max_token_len` | Ограничение длины значения в key=value паттернах |
| `max_input_size_mb` | Порог предупреждения о большом файле перед загрузкой целиком в память (по умолчанию 500). В GUI применяется и при открытии файла, и при прямой вставке/наборе текста в поле ввода |
| `pbkdf2_iterations` | Число итераций PBKDF2 для растяжения соли (по умолчанию 600 000 — актуальная рекомендация OWASP для PBKDF2-HMAC-SHA256) |
| `regex_timeout_seconds` | Таймаут защиты от ReDoS на один текстовый блок (по умолчанию 5.0; `null`/не задано — отключить) |
| `max_orphaned_regex_threads` | Верхняя граница числа одновременно "зависших" (превысивших `regex_timeout_seconds`) фоновых потоков (по умолчанию 50; `null` — не ограничивать). Защита от роста потребления памяти/потоков при систематической подаче вредоносного входа |
| `audit_log_path` | Путь к JSON Lines аудиторскому журналу операций (см. [Аудиторский журнал](#audit-log)). По умолчанию `null` — аудит отключён |
| `audit_log_max_bytes` / `audit_log_backup_count` | Ротация аудиторского журнала (по умолчанию 5 МБ × 5 файлов, как у `--log-file`) |
| `sensitive_json_keys` | Какие JSON-ключи считать чувствительными |
| `key_type_hints` | Резервная подсказка по типу значения на основе имени JSON-ключа |
| `well_known_sids` | Windows SID, которые НЕ маскируются |
| `nil_guid` | GUID, который НЕ маскируется |
| `phone_prefixes` | Международные/локальные префиксы телефонов для детекции |
| `fqdn_tlds` | Список TLD для детекции доменных имён |
| `cef_fields` | Имена полей CEF/syslog (`src=`, `suser=`...), классифицируемых по формату значения |
| `user_field_names` | Имена полей (`user=`, `login:`, `Subject:`, `Uname:`...), значение которых форсированно считается username, даже если само значение не похоже ни на один более специфичный формат — покрывает Cisco (`uname`), Checkpoint (`subject`) и типовые CEF-алиасы (`src_user`/`dst_user`) |
| `secret_field_names` | Имена полей (`password=`, `token:`...), значение которых форсированно считается секретом |
| `cef_user_fields` | Подмножество `cef_fields`, семантически всегда username (`suser`, `duser`) — обеспечивает тот же откат типа, что и `user_field_names`, но БЕЗ отдельного паттерна (иначе одно и то же поле обрабатывалось бы дважды, ломая консистентность псевдонимов) |
| `session_timeout_minutes` | (только GUI) через сколько минут бездействия очищать таблицу соответствия |

```bash
python3 -m soc_log_anonymizer anonymize -i raw.log --config myconfig.json ...
# или через переменную окружения:
SOC_ANON_CONFIG=myconfig.json python3 -m soc_log_anonymizer anonymize -i raw.log ...
```

Пример INI-эквивалента (списки — через запятую, словари — `ключ:значение`
через запятую):

```ini
[anonymizer]
org_name = acme
hash_len = 12
fqdn_tlds = com,net,local,internal
phone_prefixes = +7,+1
cef_fields = src,dst,suser,duser
sensitive_json_keys = user,ip,email
key_type_hints = user:USER,ip:IP
```

### Автопоиск конфига рядом с приложением 🔎

И CLI, и GUI **автоматически** ищут `soc_log_anonymizer.json` (приоритет)
или `soc_log_anonymizer.ini` рядом с самим приложением — при каждом
запуске заново, без необходимости каждый раз передавать `--config` или
переменную окружения:

- обычный запуск (`python -m soc_log_anonymizer`, `pip install -e .`) —
  рядом с пакетом;
- **автономная PyInstaller-сборка** (см. [Установка](#installation), "Вариант
  4") — рядом с самим `.exe`/бинарником (`sys.executable`), а не во
  временном каталоге распаковки `_MEIPASS`, который PyInstaller создаёт и
  удаляет заново при каждом запуске — туда класть конфиг бессмысленно.

Приоритет источников конфигурации (первый найденный побеждает):
`--config`/явная загрузка через диалог → переменная окружения
`SOC_ANON_CONFIG` → автопоиск рядом с приложением → значения по
умолчанию. Никакого отдельного "слежения" за файлом во время работы
не делается — "перечитывание при каждом запуске" означает буквально
это: каждый новый процесс (или нажатие "🔄 Перезагрузить с диска" на
вкладке "Конфигурация" в GUI) читает файл заново, подхватывая любые
изменения, сделанные между запусками.

<a id="config-gui"></a>
### Редактирование конфигурации в GUI ⚙️

Конфигурацию можно редактировать прямо в GUI, без внешнего текстового
редактора — вкладка "⚙ Конфигурация" показывает текущую конфигурацию как
JSON и путь к файлу (или, если файл ещё не найден/не сохранён, — путь,
куда попадёт первое сохранение и где его затем подхватит автопоиск).

| Кнопка | Действие |
|---|---|
| 📂 Открыть другой файл… | Диалог выбора и загрузка произвольного, ранее не использовавшегося файла конфигурации (единственное действие вкладки, которое не привязано к уже известному пути) |
| 💾 Сохранить | Проверяет JSON и `validate()`, при замечаниях — спрашивает подтверждение, затем сохраняет по текущему известному пути и сразу применяет к текущей сессии |
| 📁 Сохранить как… | То же самое, но с явным выбором пути через диалог |
| 🔄 Перезагрузить с диска | Отбрасывает несохранённые правки в редакторе и перечитывает файл заново — полезно, если конфиг поменяли внешним редактором прямо во время работы приложения |
| ✅ Проверить | Прогоняет `validate()` по содержимому редактора, не сохраняя и не применяя ничего — для цикла "поправил → проверил → поправил снова" |
| ↺ Сбросить к умолчаниям | Заменяет текст в редакторе значениями по умолчанию (не трогает файл на диске, пока не нажать "Сохранить") |

<a id="pseudonymization"></a>
## Принцип консистентной псевдонимизации 🔁

Главное требование к анонимизации логов для SOC: **одно и то же
значение везде должно превращаться в один и тот же псевдоним**, иначе
аналитик (и LLM) теряют возможность коррелировать события — например,
понять, что один и тот же IP выполнял разведку, а затем логинился.

Значение классифицируется по формату (`_classify_value`, результат
кэшируется через `functools.lru_cache`) перед хэшированием —
проверяется, похоже ли оно на IP, email, хэш, UUID, MAC, SID, FQDN,
Windows-логин и т.д. Псевдоним строится по определённому типу данных, а
не по имени поля или JSON-ключа, где оно было найдено. Это работает
одинаково для:

- key=value конструкций (`src=`, `suser=`, `password=`, `user=`);
- полей JSON (`"src_ip": "..."`, `"username": "..."`);
- значений в свободном тексте лога;
- одного и того же значения в разных файлах при `batch`-обработке
  (при условии одной и той же соли).

Если значение не удаётся классифицировать по формату (например, логин
без домена типа `jdoe`), используется резервная подсказка по имени
ключа (`key_type_hints` в конфиге).

Даты и временные метки не изменяются: они сохраняются для корректного
анализа порядка событий и интервалов между ними.

<a id="performance"></a>
## Производительность на больших логах 📈

- `anonymize()` / `anonymize_text()` — вся строка загружается в память;
  подходит для файлов, помещающихся в память процесса.
- `anonymize_stream()` — построчный генератор, постоянное потребление
  памяти вне зависимости от размера файла (CLI: флаг `--stream`).
- `anonymize_parallel_lines()` — параллельная обработка списка строк
  через `ProcessPoolExecutor` (CLI: `--workers N` вместе с `--stream`).
  Консистентность псевдонимов между процессами сохраняется, т.к. хэш —
  чистая функция от (HMAC-ключа, значения).
- `batch` с `--workers N` распараллеливает обработку **по файлам**
  каталога — самый практичный вариант для архива логов инцидента.
- `_classify_value` кэшируется через `functools.lru_cache(maxsize=100_000)`
  на уровне класса — повторная классификация одинаковых значений не
  пересчитывается.
- `SOCLogAnonymizer` использует `__slots__` — заметно снижает footprint
  по памяти при обработке логов с сотнями тысяч уникальных значений по
  сравнению с обычным `__dict__` на экземпляр.

<a id="security"></a>
## Security 🔐

- **Соль растягивается через PBKDF2-HMAC-SHA256** (`hashlib.pbkdf2_hmac`,
  `config.pbkdf2_iterations`, по умолчанию 600 000 итераций — актуальная
  рекомендация OWASP) перед
  использованием как ключа HMAC-SHA256 для псевдонимизации. Это
  выполняется один раз при создании `SOCLogAnonymizer`, а не на каждое
  значение, и заметно повышает стоимость offline-словарной атаки на
  экспортированный mapping-файл по сравнению с использованием соли
  напрямую. GUI предупреждает, если введённая вручную соль выглядит
  короткой/малоразнообразной.
- **Длина хэша** — 12 hex-символов (48 бит) по умолчанию, настраивается
  через `hash_len`. При коллизии (два разных значения дают одинаковый
  усечённый хэш) автоматически добавляется числовой суффикс — два
  разных значения никогда не "сливаются" под одним псевдонимом.
- **Таблица соответствия (mapping) и её экспорт (CSV/JSON) — это, по
  сути, ключ деанонимизации.** Файлы создаются с правами доступа `0600`
  (POSIX), GUI и CLI явно предупреждают перед экспортом/сохранением.
  Обращайтесь с этими файлами так же осторожно, как с исходным логом.
  `.gitignore` проекта по умолчанию исключает такие файлы.
- **Явная очистка памяти**: `SOCLogAnonymizer` — контекстный менеджер
  (`with ... as a:`), а `clear_sensitive_data()` можно вызвать вручную в
  любой момент (GUI делает это по таймауту сессии, при «Очистить всё» и
  при закрытии окна; CLI регистрирует её через `atexit` как страховку на
  случай необработанного исключения). Полной гарантии перезаписи памяти
  Python не даёт (строки иммутабельны), но это снижает время жизни
  чувствительных данных в процессе по сравнению с ожиданием обычной
  сборки мусора. SIGINT/SIGTERM в CLI перехватываются явно — иначе
  SIGTERM по умолчанию обрывает процесс, не дав `atexit`-обработчикам
  отработать.
- **`secrets.compare_digest`** используется при сравнении псевдонимов в
  разрешении коллизий хэша — сравнение хэш-подобных строк выполняется
  постоянным временем, а не обычным `==`. Практическая значимость для
  timing-атак здесь невелика (значения не секрет для собственного
  процесса), но это корректная гигиена по умолчанию для такого рода
  сравнений.
- **Права доступа к файлам соли/mapping**: и CLI, и `load_mapping()`
  проверяют (`stat`), не доступен ли файл на чтение другим пользователям
  системы (POSIX), и выводят предупреждение — не блокируют, но
  напоминают об очевидной гигиене для секретных материалов на
  многопользовательских системах.
- **Ограничение размера входного файла**: если файл, который будет
  загружен целиком в память (не через `--stream`), превышает
  `config.max_input_size_mb` (по умолчанию 500 МБ) — CLI и GUI выводят
  предупреждение (в GUI — с подтверждением перед продолжением).
- **Версионирование mapping-файлов** (`schema_version`) — будущие
  несовместимые изменения формата смогут явно предупредить вместо того,
  чтобы молча упасть или тихо испортить данные при загрузке файла,
  сохранённого другой версией инструмента.
- **Базовая защита от ReDoS**: обработка одного текстового блока
  выполняется в отдельном потоке с таймаутом
  (`config.regex_timeout_seconds`, по умолчанию 5 секунд). Python не
  может безопасно прервать уже выполняющийся regex-матчинг, поэтому при
  превышении таймаута инструмент НЕ дожидается результата и НЕ
  возвращает частично замаскированный текст (это опаснее, чем явный
  отказ) — вместо этого возвращается маркер `[ANONYMIZATION_TIMEOUT:
  ...]` и пишется предупреждение в лог. "Зависший" поток остаётся daemon-
  потоком в фоне до завершения процесса.
- Таблица соответствия в GUI хранится только в памяти процесса и
  **автоматически очищается по таймауту бездействия** (см.
  `session_timeout_minutes`). В CLI таблица не сохраняется между
  запусками автоматически — используйте `--save-mapping`/`--mapping`.
- Общеизвестные системные константы (nil GUID, well-known Windows SID —
  SYSTEM, Everyone, Administrators и т.п.) **намеренно не
  маскируются** — это не приватные данные, и их сохранение помогает LLM
  корректно интерпретировать лог.
- Gatekeeper (`verify()`) — дополнительная страховка, а не гарантия: он
  основан на тех же regex-паттернах, что и сама анонимизация, и не
  поймает то, что в принципе ими не покрыто. Финальную проверку перед
  отправкой во внешний сервис должен делать человек (или CI-пайплайн
  через `--fail-on-unsafe`).

<a id="logging"></a>
## Логирование и коды возврата 📝

CLI использует стандартный модуль `logging` вместо прямой печати в
`stderr`:

- `-v` — уровень INFO, `-vv` — DEBUG (по умолчанию — только WARNING/ERROR).
- `--log-file PATH` — журнал работы инструмента с ротацией (5 МБ × 5
  файлов, `logging.handlers.RotatingFileHandler`). В журнал пишутся
  только метаданные операций (какой файл обработан, сколько и каких
  замен сделано, предупреждения gatekeeper'а) — **не содержимое логов**.

Коды возврата:

| Код | Значение |
|---|---|
| `0` | Успех, gatekeeper не нашёл проблем (или `--fail-on-unsafe` не был передан) |
| `1` | Ошибка выполнения (файл не найден, некорректный JSON/конфиг и т.п.) |
| `2` | Успех, но gatekeeper нашёл потенциально незамаскированные данные И передан `--fail-on-unsafe` |

Это позволяет автоматически блокировать отправку логов в LLM на уровне
пайплайна/CI, а не полагаться только на визуальный просмотр вывода.

<a id="audit-log"></a>
## Аудиторский журнал 🧾

Отдельно от обычного лога приложения (`--log-file`, человекочитаемые
сообщения о ходе работы) есть опциональный **структурированный**
аудиторский журнал операций — JSON Lines, по одной записи на операцию.
Фиксирует факт и метрики, но **не содержимое**: ни исходные значения, ни
псевдонимы, ни соль в журнал не попадают — только счётчики и метаданные.
Предназначение — комплаенс/разбор "кто и когда анонимизировал логи
инцидента X", а не расследование того, что происходит ВНУТРИ самих логов.

Включается указанием пути в конфиге (по умолчанию отключён — это
осознанный opt-in):

```json
{ "audit_log_path": "/var/log/soc_log_anonymizer/audit.jsonl" }
```

Ротируется тем же механизмом, что и `--log-file` —
`logging.handlers.RotatingFileHandler`, по умолчанию 5 МБ × 5 файлов
(`audit_log_max_bytes`/`audit_log_backup_count` в конфиге) — файл не
растёт неограниченно на долгоживущем развёртывании. Текущий файл и все
файлы ротации (`audit.jsonl.1`, `audit.jsonl.2`, ...) создаются с правами
`0600` независимо от umask процесса — права фиксируются явным `chmod`
после каждой записи (сам `RotatingFileHandler` создаёт файлы через
`open()`, чьи права умолчания зависят от umask, в отличие от
`os.open`-паттерна в `save_mapping()`/`save_salt()`). Работает одинаково
в CLI (`anonymize`, `deanonymize`, `batch`) и в GUI (после
«Анонимизировать» и «Де-анонимизировать»). Пример записи:

```json
{"action": "anonymize", "source": "cli", "input": "raw.log", "org_name": "bank",
 "stats_by_type": {"IP": 12, "EMAIL": 4}, "unique_values_replaced": 14,
 "exit_code": 0, "timestamp": "2026-09-01T18:45:04+00:00",
 "tool_version": "2.1.0", "user": "alice", "host": "soc-workstation"}
```

Ограничение: в `batch --workers N` (N > 1) каждый воркер — отдельный
процесс со своим экземпляром анонимайзера (см. [ограничения](#limitations)),
поэтому агрегированная статистика по типам недоступна в этом режиме —
поля `stats_by_type`/`unique_values_replaced` в записи будут `null`, а
не вводящим в заблуждение нулём.

<a id="limitations"></a>
## Известные ограничения ⚠️

- Это **regex-based** решение, не NLP/ML-детектор сущностей. Оно не
  распознаёт имена и фамилии в свободном тексте («сотрудник Иван Петров
  сообщил...») и произвольные внутренние идентификаторы вне описанных
  форматов.
- `USER_FIELD`/`SECRET`/`CEF_KV` рассчитаны на форматы `key=value` и
  `key: value` без окружающих кавычек JSON-стиля. Если такая
  конструкция встречается внутри строки, которая сама не является
  отдельным валидным JSON/NDJSON-документом, эвристика может её не
  подхватить — используйте полноценный JSON/NDJSON вход там, где это
  возможно, чтобы сработала точная логика по ключам.
- `AUTH_USER`/`AUTH_USER_CISCO` (упоминания пользователя без `=`/`:` —
  sshd/su/Cisco) рассчитаны на конкретный, ограниченный набор конструкций
  (`Accepted/Failed password for`, `session opened for user`, `'su X'`,
  `for user "X"`, `by X on vtyN`) — это не универсальный парсер
  произвольного естественного языка. В частности, в строке su вида
  `'su root' failed for lonvick on /dev/pts/8` маскируется только
  целевой пользователь в кавычках (`root`), но не реальный инициатор
  действия (`lonvick`) — конструкция `for X on` слишком общая, чтобы
  безопасно матчить её без разбора остального контекста строки (риск
  ложных срабатываний на несвязанном тексте перевешивает пользу).
- Паттерн `USER` (`DOMAIN\user`) может технически ложно сработать на
  произвольном тексте вида `Слово\ДругоеСлово` — унаследованная
  особенность формата Windows-логинов.
- `PHONE`/`FQDN` покрывают только префиксы/TLD, перечисленные в
  конфигурации — расширяйте под свою специфику логов.
- `--stream` и построчный `anonymize_stream()` не разбирают JSON,
  растянутый на много строк без построчной структуры (не NDJSON) — для
  таких файлов используйте обычный `anonymize()` (весь файл в памяти).
- `anonymize_parallel_lines()` разрешает коллизии хэша независимо в
  каждом воркере — при реальной коллизии (крайне маловероятной при
  12-символьном HMAC) в разных чанках теоретически возможны разные
  суффиксы для одного и того же коллизирующего хэша.
- Защита от ReDoS (`regex_timeout_seconds`) не может принудительно
  прервать уже запущенный regex-матчинг (ограничение CPython/GIL) —
  она гарантирует, что вызывающий код не получит частично
  замаскированный текст и не будет заблокирован дольше таймаута, но
  "зависший" поток продолжает потреблять CPU в фоне до завершения
  процесса.
- Кэш классификации значений (`_classify_value`) — на уровне ЭКЗЕМПЛЯРА
  (`self._classify_cache`, с верхним лимитом размера), а не общеклассовый
  `lru_cache` — это осознанное решение против утечки памяти: общеклассовый
  кэш, ключующийся в т.ч. по самому экземпляру, держал бы сильную ссылку
  на каждый созданный `SOCLogAnonymizer` до явного `cache_clear()` —
  ощутимо при частом пересоздании экземпляров (типичный сценарий для GUI
  при смене соли/конфигурации). `clear_sensitive_data()` очищает только
  кэш своего экземпляра, не затрагивая другие активные в этом процессе.
- Число итераций PBKDF2 (по умолчанию 600 000 — актуальная рекомендация
  OWASP для PBKDF2-HMAC-SHA256) выполняется один раз при создании
  `SOCLogAnonymizer` и добавляет заметную, но некритичную задержку старта
  (обычно десятые доли секунды). В параллельных путях
  (`anonymize_parallel_lines`, `batch --workers N`) это НЕ умножается на
  число воркеров/чанков/файлов: ключ выводится один раз в родительском
  процессе и передаётся уже готовым (см. `_prederived_key` в
  `SOCLogAnonymizer.__init__`) — при массовом батче из сотен файлов это
  избавляет от сотен избыточных прогонов ради одного и того же ключа. При
  самостоятельном создании множества короткоживущих экземпляров с ОДНОЙ
  и той же солью вне этих путей (собственный код поверх библиотеки) тот
  же приём стоит применить вручную, либо просто переиспользовать один
  экземпляр вместо пересоздания.
- `--mmap`/`iter_lines_mmap()` определяют кодировку по первому 64КБ-
  сэмплу файла и не поддерживают UTF-16 без BOM в самом начале (сэмпл
  может быть обрезан посередине двухбайтового символа) — для таких
  файлов используйте обычный `read_file_auto_encoding()` (полная
  загрузка) или заранее перекодируйте файл в UTF-8.
- **Drag-and-drop файлов в GUI сознательно не реализован.** Ванильный
  `tkinter` не имеет кроссплатформенной поддержки приёма файлов из
  проводника/Finder без стороннего Tcl-расширения (`tkdnd`), а
  реализация DnD только для части платформ создавала бы больше путаницы
  (работает тут, не работает там), чем пользы — при заданном ограничении
  "только стандартная библиотека" правильнее явно предложить кнопку
  «Открыть» (`Ctrl+O`) или вставку текста, чем притворяться, что DnD
  работает везде.
- Параллельная обработка (`ProcessPoolExecutor`) передаёт между
  процессами обычные Python-строки (через pickle), а не
  `multiprocessing.shared_memory` — для типичных размеров логов (до
  единиц ГБ на чанк) накладные расходы pickle несущественны по
  сравнению со сложностью и рисками собственной схемы индексации
  переменной длины строк в разделяемой памяти.

## Тесты 🧪

```bash
python3 -m unittest discover -s tests -v
```

Покрывают: консистентность псевдонимов между CEF/JSON/свободным
текстом, обработку коллизий, whitelist well-known SID/GUID, полноту
gatekeeper-проверки, roundtrip анонимизация→деанонимизация, сохранение
и загрузку mapping-таблицы (включая `schema_version`), статистику,
построчный стриминг и параллельную обработку (сверка результата с
последовательной), загрузку JSON/INI-конфигурации и её валидацию,
`__slots__`, контекстный менеджер и очистку памяти, таймаут-защиту от
ReDoS, gzip-архивы и mmap-стриминг (`tests/test_io_utils.py`), сам CLI
(`unittest.mock`: exit-коды, `--version`, переменные окружения,
multi-file glob, `batch` (включая gzip-вход), `validate-config`),
doctest-примеры из `anonymizer.py` (интегрированы в discovery через
`tests/test_doctests.py`), чистую логику GUI без зависимости от
`tkinter` (`tests/test_gui_logic.py` — статус-чипы, прогресс,
предупреждения) и fuzz-тест на стандартном `random` с фиксированным
seed (`tests/test_fuzz.py` — 200 случайных логов, инвариант "gatekeeper
всегда доволен после anonymize()" + roundtrip-инвариант деанонимизации).

Дополнительно, без сторонних инструментов:

```bash
# Явный прогон doctest-примеров
python3 -c "import doctest, soc_log_anonymizer.anonymizer as m; doctest.testmod(m, verbose=True)"

# Базовый coverage-отчёт средствами стандартной библиотеки (без coverage.py)
python3 -m trace --count --coverdir=cov -m unittest discover -s tests

# Профилирование самого инструмента на реальном логе
python3 -m soc_log_anonymizer anonymize -i big.log --salt-file salt.txt \
    --profile --profile-memory -v -o /dev/null
```

### Continuous Integration 🔄

`.github/workflows/ci.yml` прогоняет на каждый push/PR в `main`:

| Job | Что проверяет |
|---|---|
| `test` | Матрица Ubuntu + Windows × Python 3.9–3.13: компиляция, `unittest discover`, doctest, `validate-config` на обоих примерах конфига, `--version`, полный CLI-цикл (anonymize → deanonymize roundtrip → batch) |
| `gzip-and-stream` | `.gz`-вход в обычном режиме, `--stream`, `--stream --mmap` |
| `zipapp` | Сборка `.pyz` и smoke-тест собранного архива |
| `pyinstaller-build` | Сборка автономного GUI-бинарника (`packaging/soc_log_anonymizer_gui.spec`) — headless-раннер не запускает сам GUI, но ловит регрессии в spec/hiddenimports/точке входа на этапе сборки |
| `pip-install` | `pip install -e .` и запуск установленной команды `soc-log-anonymizer` |
| `macos` | Полный набор тестов на macOS |

Тесты не требуют установленного `tkinter` ни на одном раннере: логика
GUI, зависящая от tkinter, изолирована в `gui.py`, а `gui_logic.py` (и
весь остальной пакет) от него не зависит; `cli.py` импортирует `gui.py`
лениво (внутри функции, не на уровне модуля).
